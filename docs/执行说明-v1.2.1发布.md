## 4. 发布

### 4.1 更新通道的真实规则（务必按这个命名，否则模块内查不到更新）

代码只读 `https://api.github.com/repos/<owner>/<repo>/releases/latest`，逻辑如下：

- **tag 名**：支持 `103-1.2.1`、`v1.2.1`、`1.2.1` 三种写法；正则 `^(\d{2,6})-` 会把数字前缀当作 versionCode。**必须用 `103-1.2.1`**，因为解析出 versionCode 时按 `103 > 本地 versionCode` 判定新版本，比字符串比较可靠。
- **资产筛选**：文件名以小写 `.apk` 结尾，且不含 `mapping`、不含 `debug`；多个时优先挑名字里包含版本号字符串 `1.2.1` 的那个。
  → 所以 APK 资产名用 **`TGAutoSign-v1.2.1-release.apk`**。附带上传 `sha256sum.txt`、`CHANGELOG` 等无妨（不是 `.apk` 结尾，不会被选中）。
- **下载地址**：直接用资产 `browser_download_url`，代码不加任何镜像前缀。用户侧网络到 GitHub 不通时下载会失败，这是已知限制，不要试图在产物里塞代理地址。
- **检查频率**：开机后台静默检查 12 小时最多一次；用户在 TG 里发 `/jmb → 🔄 检查更新` 时无视冷却。测试时若"没提示"，先确认是不是被冷却挡住了，用手动检查。
- 两个仓库的 tag 与资产名保持一致，第一跳（`Xposed-Modules-Repo`）优先命中。

### 4.2 推源码 + 建 tag

```bash
git remote -v                                  # 确认两个 remote；本机没有凭据时用你自己的 gh login / SSH key
git push origin master                         # 只推 fast-forward，禁止 --force
git push origin v1.2.0 v1.2.1 2>/dev/null || git tag v1.2.1 && git push origin v1.2.1
# tag v1.2.1 必须指向 v1.2.1 的那个 feat 提交（本工程 HEAD）
```

```bash

gh release create 103-1.2.1 "$APK" \

  --title "v1.2.1 (103)" \

# 模块发布仓库（更新检查的第一跳）
```

模块内所有管理入口都在 Telegram 里发消息 `/jmb` 弹出的对话框菜单，**没有独立管理 App，也没有桌面小组件**（v1.2.1 已把这些不可达的旧代码删除，找不到它们是预期的）。

按顺序做，每条记录实际现象：

1. 老版 v1.2.0 设备上**覆盖安装** v1.2.1（不要先卸载）。发 `/jmb → 📋 目标列表`，确认原有目标与"已签"状态还在。
2. 发 `/jmb → 🔄 检查更新`：应显示"已是最新 v1.2.1"。
3. 把测试设备的更新源指向仍只有 103 的仓库前，先在装 v1.2.0 的设备上验证：`/jmb → 🔄 检查更新` 应提示发现 v1.2.1，出现子项 `⬇️ 下载 v1.2.1 安装包`；点它 → 落到系统"下载"目录 → 自动拉起系统安装器 → 覆盖安装成功（**这一步同时反证 3.2 的签名指纹正确**：指纹不对时系统会拒绝覆盖安装）。
4. 发 `/jmb → 📤 导出配置`：应回报写入的 json 文件名（形如 `TGAutoSign-config-1.2.1-<时间戳>.json`，位置在系统"下载"及 `Android/data/org.telegram.messenger/files/tgautosign/`）。
5. 换账号或清空数据后发 `/jmb → 📥 导入配置`：应读到最新导出文件，且**只合并、不清空**当前目标。
6. 正常签到回归：到点后目标 bot 应照常收到签到指令，成功即停；已签目标显示"已签"。
7. 断网测试：飞行模式下发 `/jmb → 🔄 检查更新`，应只报检查失败，签到主流程不受影响、无崩溃、无 ANR。
8. 日志抽查：`/jmb → 📄 运行日志`（最近 200 行）里应能看到模块加载行 `=== TGAutoSign 模块 v1.2.1 (jmb界面版) 已加载 ===`。
